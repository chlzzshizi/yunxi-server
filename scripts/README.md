# scripts/ —— 真机接口验收脚本

这些不是单元测试。单元测试跑在 Mockito 里、不碰 Spring 也不碰数据库；**这里的每个脚本都要打真机**：一个跑在 8081 上的后端 + Docker 里的 MySQL 和 Redis。它们验证的是"接起来到底对不对"——SQL 真的写进去了吗、状态真的推进了吗、越权真的被挡了吗。

## 为什么它们现在住在仓库里（而不是某个人的 `C:\tmp`）

2026-09-11 之前，这批脚本住在 `C:\tmp` 下。后果是它们**不在版本管理里**：

- 改了共享行为（比如 2026-09-10 的"后端算价"），没有任何东西提醒你这些脚本会受影响；
- `verify-race.sh` 从 `db11044` 起就是坏的，直到隔了一整轮口径修订才被发现——因为它压根没人跑。

那次踩的坑记在 `docs/bug-record.md` 的 **Bug 21 / Bug 22**。Bug 21 的教训原文就是"改了共享行为要把受影响的**全部**脚本列出来重跑"，但当时只在 5 个脚本里改了 1 个——**结论正确 + 没有执行 = 没修**，于是同一个根因换了张脸又犯一次（Bug 22：`verify-race.sh` 把"准备失败"报成"并发失灵"，把排查方向指反了）。

搬进仓库就是为了让改动能跟代码进同一次提交、能看见 diff、能被 review。

## 前置

```bash
docker compose up -d      # yunxi-mysql(3306) + yunxi-redis(6379)
# 后端已在 8081 起着
```

- **必须用 Git Bash 跑**。PowerShell 里的 `bash` 指向 WSL，而 WSL 里既没有 docker 命令也连不上宿主机的 localhost 代理（实测报 `execvpe(/bin/bash) failed`）。
- **后端必须是"已经跑过全部迁移"的那一版**。Flyway 在应用启动时才执行迁移 —— 换了迁移文件却不重启后端，DB 还停在上一个版本，症状是最难认的那种：`verify-coupons.sh` 会全军覆没在 `Unknown column 'used_time'` 上（B3/C2/F3），看起来像"抵扣逻辑写错了"，其实是后端没重启。跑之前对一眼：

  ```bash
  docker exec yunxi-mysql mysql -uroot -pqwaszx123 yunxi -N --default-character-set=utf8mb4 \
    -e "select group_concat(version order by installed_rank) from flyway_schema_history;"
  ```

  **别用 `select max(version)`**：`flyway_schema_history.version` 是 **VARCHAR**，`max` 走字符串比较，于是 `'9' > '10'` —— 库里有 V10 的时候它会告诉你最大版本是 9。2026-09-13 就是这么被它骗了一下的（当时差点把"V10 已执行"读成"后端没重启"）。要看装了哪些版本，`group_concat` 按 `installed_rank` 排出来才是真相。

  另一个更直接的判据：**新加的端点会不会回答**。`curl -s -X POST localhost:8081/api/orders/1/express -H "Authorization: Bearer x"` 回 `Token 无效或已过期`（401）说明这条路由在；回 404 说明跑的还是旧包。
- 需要 `curl`；脚本用 `docker exec yunxi-mysql mysql` 直连数据库核对"落库真相"。
- 只有 `bench-coupon.sh` 额外要 **JDK 21+**（`scripts/loadgen/LoadGen.java` 用虚拟线程）。它优先认 `JAVA_HOME`，因为 **PATH 上的 `java` 在这台机器上是 1.8**。九个 `verify-*.sh` 都不需要 java。
- 演示账号：`manager/admin123`（店长）、`admin/admin123`（管理员）。

## 怎么跑

**从任何目录都行**，路径一律相对脚本自身：

```bash
bash scripts/verify-orders.sh
```

脚本中途产生的中间文件（替换占位符后的请求体、并发请求的响应）写到 `${TMPDIR:-/tmp}/yunxi-e2e/`，不污染仓库。

## 压测脚本：`bench-coupon.sh`（2026-09-18）

上面九个脚本证明的是**正确性**，一个都没测过**吞吐** —— 全仓库检索过 `TPS|QPS|吞吐|响应时间`，零命中。而"抢券高并发"是这个项目唯一挂着"高并发"四个字的功能，面试问"多少 TPS"原本答不上来。`bench-coupon.sh` 补的就是这一半。

```bash
bash scripts/bench-coupon.sh                    # 默认 500 并发抢 100 库存
N=200 STOCK=100 bash scripts/bench-coupon.sh    # 改并发和库存
```

> 跑**并发曲线**（比较不同并发下的吞吐）时让 `STOCK = N/2`，把成功率固定成 50%。否则 N=100 时 100% 成功、N=500 时只有 20% 成功，写库次数完全不同，曲线会被成功率带偏而不是被并发数带偏。

| 脚本 | 断言数 | 证明什么 | 会写脏数据吗 |
|---|---|---|---|
| `bench-coupon.sh` | 10 | **不超卖**（成功数恰好 = 库存，多了少了都报错）+ **扣减行为符合设计**（库存键停在 `库存−并发`，验证「减了不回补」那条注释）+ **400 的原因是「抢完」不是「重复抢」**（两者 code 都是 400，计数分不出来，只有看 message 才能分开）+ **去重挡得住**（同一顾客并发 N 次恰好成 1 次）。附带产出 TPS / P50 / P95 / P99 | **会**：每跑一次新发 4 张券 + N 个顾客，累积型 |

### 为什么要自己写压测器，而不是装 wrk / hey

**抢券压测每个请求必须是不同顾客。** 同一个顾客并发发 N 次会全部被 Redis Set（`coupon:grabbed:*`）和数据库唯一键（`uk_coupon_customer`）挡下，测到的是"去重生效"而不是"库存竞争" —— 那是个假的高并发测试，数字再好看也没意义。而 wrk/hey 只会对同一个 URL 反复发同一个请求头，喂不了 N 个不同 token（`hey` 只能配一个 `-H`，还是静态的）。

`scripts/loadgen/LoadGen.java` 是 JDK 21 虚拟线程写的，**零依赖、单文件**（`java LoadGen.java` 直接跑），"一个请求一个线程、一个线程一个 token"写起来和同步代码一样。token 由 bash 侧走真实登录拿（`login_or_register`，同 `verify-coupons.sh`），Java 侧只管同时开火和计时。

### 这个脚本带来的三个新坑

**一、所有轮次必须在同一个 JVM 里跑。** 这条最贵，放第一个。

第一版的 `LoadGen` 用法是 `java LoadGen.java <url> <tokens> [n] [label]`，由 `bench-coupon.sh` **每轮调一次、开一个新 JVM**。跑出来三轮 TPS 是 279 / 305 / 303，当时当成"服务端吞吐很稳定"写进了报告 —— 是错的。

揭穿它的办法是造一个**瞬时响应的对照服务端**（`com.sun.net.httpserver`，20 行，不碰库不碰 Redis），拿 `LoadGen` 打它：**N=1 要 116ms，比打真实应用还慢**。然后用 curl 量同一个真实请求：11ms。再在同一个 JVM 里连跑四轮 N=50：p50 是 **344ms → 32ms → 23ms → 58ms**，第一轮比第三轮慢 15 倍。

三轮数字一样，不是因为服务端稳定，是**三轮一样冷**。那个"预热轮"只暖到了服务端（同一个 Spring 进程），客户端每轮都是刚启动的 JVM —— JIT 没编译、类没加载、连接池是空的。

现在 `LoadGen` 的参数是 `<并发数> <标签> <url> <token文件> ...`，**一个 JVM 顺序跑完所有轮**，共享一个 `HttpClient`（连接池跨轮续上）。`bench-coupon.sh` 因此发 **4 张券**：预热1 / 预热2 / 测量 / 对照。为什么预热两轮不是一轮——实测第二轮还没完全收敛。

**收敛与否从输出里直接看得到**，这是采纳这个设计最实际的理由：

```
预热1 295.71 TPS / p50 1467ms     ← 冷
预热2 845.81 TPS / p50  425ms     ← 已热
测量  872.42 TPS / p50  413ms     ← 与预热2 只差 3%，可以采信
```

**前两轮和测量轮的差距就是"这次数字能不能用"的判据。** 差距大就加预热轮重跑，别把没热透的数字填进文档。

完整过程记在 `docs/bug-record.md` **Bug 31**。教训的核心不是"记得预热"，而是**"这个数字是从哪台机器、哪个进程、第几轮出来的"和数字一样重要** —— 和 Bug 29（往文档里填没跑出来的数字）是同一个病：绿/好看 这个信号和"真的量过"脱钩了。

**二、Java 的 stdout 在这台机器上不是 UTF-8。** 实测 `System.out.println("已抢完")` 打到 Git Bash 里是乱码（Windows 控制台代码页是 GBK）。而压测的输出是要被 bash 拿去断言的，转码一次断言就成了玄学。所以 **`LoadGen.java` 的输出一律是 ASCII**，响应里的中文 message 走 **URL 百分号编码**（编码的是 UTF-8 字节）：

| 中文 | 编码后的字节 | 出处 |
|---|---|---|
| 已抢完 | `%E5%B7%B2%E6%8A%A2%E5%AE%8C` | `CouponAppService.grabCoupon` 库存扣成负数时 |
| 你已经抢过了 | `%E4%BD%A0%E5%B7%B2%E7%BB%8F%E6%8A%A2%E8%BF%87%E4%BA%86` | 同上，Redis Set 命中 / 撞唯一键时 |

A7/A8 就是拿这两串比对的。**注意这和"脚本内可以放心写中文"不冲突**：坏掉的只有 Java 进程那一路 stdout，bash 自己的 `echo`/`printf` 一直是字节安全的。

**三、后端起的时候必须压掉 DEBUG 日志。** `application.yml:50` 是 `logging.level.com.yunxi: debug`，而 MyBatis mapper 的包名就在 `com.yunxi` 下 —— 500 并发时每条 `selectById`/`insert` 都会打一行日志，**不关掉你测的是 logback，不是 Redis**。不改配置文件，走 `-D` 覆盖：

```bash
cd yunxi-interfaces && ../mvnw spring-boot:run \
  -Dspring-boot.run.jvmArguments="-Dlogging.level.com.yunxi=warn"
```

脚本会在跑之前检查 JDK 版本（要 21+，虚拟线程）—— **PATH 上的 `java` 在这台机器上是 1.8**，所以它优先认 `JAVA_HOME`。

### 读数字时必须带上的边界

脚本最后会把这几条打出来，**写进简历/报告时不能省**，省了数字就是吹的：

- **压测端和服务端同机**（12 核）。`LoadGen` 的 JVM 和 Spring Boot、MySQL、Redis 抢同一批核 —— 测出来的是**下限**，不是这套代码的上限。
- **Tomcat 默认 `max-threads=200`、Druid `max-active=20`**（`application.yml` 没配线程池），DEBUG 日志已用 `-D` 压掉。
- **两条启动路径都会加上 `-XX:TieredStopAtLevel=1`**（IntelliJ 的 Spring Boot 运行配置、`spring-boot:run` 的 `optimizedLaunch` 默认值，两条都实测验过；pom 里没配，`MAVEN_OPTS` 是空的）。也就是说**这份文档里的所有 TPS 都是在 C1-only 编译下测出来的** —— 它大概是偏低的，但偏多少没人量过，这是本页所有数字上一个没被消掉的边界。
- **单次采样不能信。** 同一个并发下重复跑，TPS 极差最大到 **±22%**（2026-09-18 实测：N=500、同一个配置跑 6 遍是 851–1058）。**要报就报多次的中位数，别报最好的一次。** 24 次运行里有 1 次离群到 p50 1171ms —— 那是机器在打嗝，不是代码坏了，但它足以让单次采样得出完全错误的结论。
- **这台机器分辨不出 20% 以下的差异。** 实测抖动落在 4.8%–22.3%，**比想测的效应还大**。所以下面那组对照实验里"测不出来"要读成**"这台机器没能力判定"**，不是"两者一样"。
- **预热两轮的数字要一起报告**（脚本已经打出来了）。差距大说明 JIT 还没热透，测量轮不能采信。

### 跑出来的是什么（2026-09-18，24 次运行）

**500 并发抢 100 张券、0 超卖**（两遍）：872 / 777 TPS，p50 413 / 497ms，p99 536 / 617ms。

**并发曲线**（每点 3 遍取中位，`STOCK = N/2` 固定 50% 成功率）：

| 并发 | 10 | 20 | 25 | 50 | 100 | 200 | 300 | 500 |
|---|---|---|---|---|---|---|---|---|
| TPS | 320 | 434 | 525 | 594 | **670** | 649 | 568 | 733 |
| p50 | 19ms | 29ms | 32ms | 53ms | 93ms | 188ms | 350ms | 538ms |
| p99 | 31ms | 46ms | 48ms | 84ms | 146ms | 300ms | 494ms | 671ms |

三条结论：

1. **吞吐在 N≈100 就吃满了**：10→100 翻倍（320→670），100→500 只涨 9%（568–733 全在噪声带内）。加到 5 倍并发，买到的基本是零吞吐。
2. **过了拐点 `p50 ≈ N 毫秒`**：八个点里六个落在 N 的 0.93–1.28 倍。这是"吞吐固定、延迟 = 并发 ÷ 吞吐"的标准形态，不是拟合出来的。
3. **形状是健康的**：没有悬崖、没有雪崩点。24 次运行**全部 10 项断言通过**，包括那次离群（TPS 234 / p50 1171ms）**依然 0 超卖** —— 性能抖动和正确性完全解耦。

### 瓶颈在哪：曲线只能给推断，真跑对照才给结论（2026-09-18）

24 次曲线原本是这样推的：Tomcat `max-threads=200` 对不上（饱和在 N≈100，那时线程数远没到 200）、Druid `max-active=20` 不可能是唯一的墙（N=20 就越过它了，吞吐还在涨）。**但那两步都只是推断** —— 曲线饱和可以有一百种原因，"参数对不上"不等于"参数不是因"。

所以补了一组真对照（N=500，每点 3–6 遍取中位，同一天同一台机器）：

| 配置 | 轮次 | 中位 TPS | 范围 |
|---|---|---|---|
| A 平台线程 / Druid 20（基线） | 3 | 857 | 764–858 |
| B **虚拟线程** / Druid 20 | 4 | 885 | 762–915 |
| C 虚拟线程 / **Druid 50** | 6 | 929 | 851–1058 |

- **Tomcat `max-threads=200` —— 实测排除。** B 组把执行线程换成虚拟线程（`jcmd Thread.print` 验过：`http-nio-8081-exec-*` 归零，只剩 `Acceptor`/`Poller`）——**200 个线程那道闸整个消失了**，吞吐纹丝不动（885 vs 857，两组范围完全重叠）。闸拆了流量不变，它就**不是**墙。这条从推断升级成了因果。
- **Druid `max-active=20` —— 测不出来。** C 组把池子开到 50（`Max_used_connections` 从 21 涨到 51，证明真的开上去了），+5.0%，两组范围重叠。**是"这台机器分辨不出 5%"，不是"两者没差别"** —— 呼应上面那条分辨力边界。虚拟线程那组 p50 从 427ms 降到 325ms，是这轮里唯一一个稳定跑出方向来的信号。
- 剩下最可能是 **12 核本身**（670 TPS 摊下来每请求约 6ms CPU，对 Spring Boot + MyBatis 是合理量级）。**这一条仍然只是推断** —— 它没法用"改个参数再跑一轮"来证伪。

**服务端冷启动是 1.87 倍的变量**（记在 Bug 32）。同一个配置（虚拟线程），重启后第一次跑 **443.88 TPS**，热起来之后四次是 775.06 / 821.61 / 842.68 / 846.88（中位 **832**）。所以**预热协议必须包含服务端，不只是压测器的 JVM** —— 判据仍然是收敛：`预热2 与测量只差 3%` 才算热透，`188 → 337 → 444` 这种还在爬的数列一律不采信。这一条差点让我把"虚拟线程更慢"写进报告（444 vs 记录在案的 649），是同一天重测基线才拦下来的。

**顺带发现一个优化点（只发现，没改）：** `CouponAppService.grabCoupon` 第一步是无条件的 `couponMapper.selectById(couponId)`，**每个请求都走一次**。500 并发 = 500 次 select + 约 250 次 insert ≈ **750 次 DB 往返**，其中约 1/3 是替那 250 个注定拿 400 的请求白查的。券活动是极热的小数据（按 id 查、极少变），缓存它就能砍掉这部分。本轮没动业务代码。

### 第三个坑：`db()` 的字集（2026-09-12）

**每个**访问数据库的助手（`db()` / `dbFile()` / `dbQ()` / 内联的 `docker exec`）现在都带 `--default-character-set=utf8mb4`，**别把这个参数删了**。删掉之后 mysql 命令行会按客户端默认的 latin1 收发，中文两个方向都坏：

- 写 → UTF-8 字节被当 latin1 解读再转存 = 双重编码（实测存进去是 `C3A4C2BAE28098…`）
- 读 → 真 UTF-8 的中文转不成 latin1，整串变成 `?????`

**最阴的是双重编码在「读」的时候会抵消回去**：存的是乱的，`SELECT` 出来却是好的。于是"列表里不含这个店名"这类断言**无条件通过**——库里那个名字本来就写不出正确的那六个字，怎么断言都找不到它。`verify-stores.sh` 的 A3 当时就是这么假绿的。

所以造完中文数据要**断言库里的字节**（`verify-stores.sh` 的准备守卫 + A3c 就是干这个的），不能只看"读出来是对的"。

**2026-09-18 补一条更基础的**：`--default-character-set=utf8mb4` 只管"字节怎么解码"，**管不了"字节有没有被改过"**。`db()` 的 SQL 是**命令行参数**，而 `docker` 是原生 Windows exe —— MSYS2 会按当前代码页（中文系统 = GBK）先把参数转一遍，所以

```bash
db "select id from stores where name='云洗中央门店';"   # ← 查的是 GBK 字节序列
```

**永远查不到**（库里是 UTF-8）。而且它不是报错，是**静默返回空** —— 于是"列表里有没有这家店"这类断言会无条件地说没有，正是上面那种假绿。

规矩：**SQL 里有中文就用 `dbQ`（走 stdin），没有才用 `db`**。`verify-admin.sh` 把两个助手并排放着、名字上就能看出区别，就是为了让这件事在调用点上可见。同理，带中文的 SQL 一律不要写进 `-e "..."`。

> 完整的两类编码坑（还有一类是 MSYS2 把非 ASCII 命令行参数转成 GBK，影响 `curl -d`）写在 `verify-stores.sh` 的文件头，要改脚本先读那段。

### 第四个坑：自愈语句只修了**一半**的中文列（2026-09-13，Bug 30）

上面那条"造完中文数据要断言字节"只说了**验**，没说**修**。补一条同样硬的要求：**修的时候要整行修，验的时候要整行验。**

两个脚本造脚手架门店时都是这个形状：

```sql
insert ignore into stores (id,name,address) values (2,'二号门店','验收用');
update stores set name='二号门店' where id=2;   -- ← 只补了 name
```

insert 里的中文列有**两个**，自愈 update 只写了**一个**。于是 `name` 每次跑都被写回正确字节，`address` 一次都没被碰过 —— 两个门店的地址乱码从 09-12 一直躺到 09-13，是**用户在前端下拉框里肉眼**撞见的，八轮脚本全绿、单测 172 全绿都没喊。

区别不在 SQL 写法，在**谁盯着它**：`name` 有准备守卫和 A3c 两条断言看着，烂了会立刻停；`address` 一条断言都没有。而用这家店的 `verify-orders.sh` F 段连店名都不看（它只看订单），所以"脚本全绿"和"库里有乱码"**同时为真，两件事不冲突**。

所以看着 `insert ignore` + `update` 这种自愈组合时，检查方法是机械的、不需要判断力：**把 insert 里所有的非 ASCII 列列出来，逐个问"谁在盯着它"**。答不出来的那几列，就是正在烂或者即将烂的那几列。

顺着这条查出**三处**，第三处比前两处更根本 —— `verify-auth.sh` 造停用账号时用的是

```bash
docker exec yunxi-mysql mysql -uroot -pqwaszx123 yunxi -e \
  "insert ignore into staff (...) values (98,'mgr_disabled','…','停用店长',1,1,0);"
```

中文直接在 `-e` 的参数里，而且**连 `--default-character-set=utf8mb4` 都没有** —— 两个编码坑一起踩，也没有任何自愈语句，`staff id=98` 的名字从建出来那天就是乱的。那处的问题不在"自愈漏了一列"，而在**写进去的这条路本身会转码**：光加守卫没用，守卫会一直正确地失败。所以先把它改成 `printf | docker exec -i … --default-character-set=utf8mb4`，再补自愈和守卫。

**改这三个脚本时，"正跑一次"是不够的**：自愈语句刚把数据写对，紧接着的守卫读出来当然是对的 —— 这样只能证明"没崩"，证明不了守卫会拦。要**先把那行数据人为弄成乱码、只跑守卫**，看它退出码 1 并指名是哪一列。三个脚本都这么正反各跑了一次（Bug 30 有记录）。

### 表格里的断言数是快照

上面那张表的数字是**最后一次全量跑的结果**，不是自动维护的。改了脚本就得回来手工更新——这不是理想状态，但它至少是一个能被 review 的 diff；不写反而没人知道哪个脚本变过。跑一遍对不上就顺手改了。

## 写脚本时的两条硬要求

1. **准备阶段失败要立刻喊停，不能让它继续跑成断言失败。** 拿不到订单 id、状态没到预期、登录没拿到 token —— 直接打印原始响应并 `exit 1`。否则报出来的错会指向完全无关的地方（Bug 22 就是这么把两个 404 读成"CAS 失灵"的）。
2. **中间的 `404 资源不存在` 出现在"资源一定存在"的用例里，本身就是强信号。** 别把它当成"断言没通过"轻轻放过。

`verify-coupons.sh` 的脚手架是**累积型**，和前三个不一样：它每跑一次就新发 4 张券（**不改 id、不复用**），跑 N 次库里就有 4N 张叫做 `CPN-E2E-*` / 「开业五折券」的券，顾客A 名下一堆已用掉的抢券记录。之所以不复用固定 id：券的可用性绑定在"这个批次还能不能抢"上，复用就得每次重置 Redis 的库存键和已抢集合，那等于把"准备阶段"变成一段容易写错的 SQL；而每轮新发一张的代价只是几张废券。**要干净数据只有 `down -v`**。

`bench-coupon.sh` 比它更狠：**每跑一次多 N 个顾客和 4 张券**（券叫 `BENCH-*`，默认 N=500）。用的是同一套"每轮新发、不复用 id"的理由，而且这里**非这样不可** —— 库存键在第一轮跑完就停在 `库存−并发` 那个负数上了，复用同一张券就得先把它重置回正数，那正好把 A6 要验的东西手动抹掉。券是 4 张而不是 3 张，因为客户端需要两轮预热（见上面坑一）。顾客的手机号带 epoch 前缀（`139` + 10 位秒 + 3 位序号），所以**重复跑不会撞 `uk_phone`**，脚本可以连着跑。

> union all
> select '压测顾客抢过非 BENCH 券?', count(*) from coupon_grabs g join customers cu on cu.id=g.customer_id
>   join coupons c on c.id=g.coupon_id
>   where cu.phone like '139%' and length(cu.phone)=16 and c.name not like 'BENCH-%'
> union all
> select 'BENCH 券被人下过单?', count(*) from coupon_grabs g join coupons c on c.id=g.coupon_id
>   where c.name like 'BENCH-%' and g.used_order_id is not null
> union all
> select 'BENCH 券被非压测顾客抢过?', count(*) from coupon_grabs g join coupons c on c.id=g.coupon_id
>   join customers cu on cu.id=g.customer_id
>   where c.name like 'BENCH-%' and not (cu.phone like '139%' and length(cu.phone)=16);
> ```
>
> ### ⚠️ 判据必须用长度卡死，**不能只写 `like '139%'`**
>
> 压测手机号 = `139` + 10 位秒 + 3 位序号 = **16 字符**。
>
> 库里**真的有 11 位的 139 号段顾客**：`13900000011` / `13900000012`（id 5716 / 5717），是 `verify-coupons.sh` 的**顾客A** —— `orders` 里那几张单、`coupon_grabs` 里那几条非 BENCH 的记录，全挂在它名下。**只写 `like '139%'` 会把它俩一起删掉**；而且删完当轮脚本照样绿（下一轮会重新注册），要等下次跑 `verify-coupons.sh` 的 F 段真去用券时才炸 —— 典型的"删完不报错、隔一轮才响"。
>
> 还有一处同形状的陷阱：脚本守卫里那句探测用的 `13900000000` 只有 **11 字符** —— 万一哪次注册成功了它也会躺在库里，而它不是压测造的。
>
> **两个都靠 `length(phone) = 16` 躲开。** `verify-auth.sh` 要的 `13700000002`（WalkIn，11 位）、`13800138000`（张三）也都不在这个形状里。
>
> ### 删完必须验（不能只看行数掉了）
>
> ```bash
> bash scripts/verify-coupons.sh   # 券域的 32 项：确认顾客A 和 CPN-E2E 那批还在
> bash scripts/verify-auth.sh      # WalkIn 那条分支：确认无密码顾客没被误伤
> ```
>
> 2026-09-18 清理后这两个分别是 **32/32** 和 **36/36**。清理**只要跑这两个** —— 它俩的射程正好覆盖被删数据的两个邻居（顾客A / WalkIn）；其余脚本的脚手架（门店 2/99、员工 98/99）压根不在 139 号段里。

跑压测**不改任何业务代码**，所以上面九个脚本和 `mvn -o test` 的基线不受影响；但按"验收门是全部"的规矩，跑完压测要重跑一次 `verify-coupons.sh`，确认券域没被压测搞脏。
