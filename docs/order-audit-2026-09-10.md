# 订单模块盘点：实现 vs 设计文档（2026-09-10）

> 方法：纯静态审计。逐行读了 `Order`(domain) / `OrderAppService` / `OrderController` / `OrderRepositoryImpl` / `OrderPO` / `OrderMapper.xml` / `OrderItemMapper.xml` / 枚举 / DTO / V1 建表 SQL，逐条对照设计文档 §5（状态机）、§4.5+§10.6（定价）、§10.4（顾客身份）、§10.5（分拣上架）。
> 运行时行为验证（含状态机全路径）安排在下一步做，本文不含运行结论。

## 一、总体结论

**主链路（1→2→3→4→分叉→终态）的状态机骨架是正确的，前置校验（分叉路由、未付清拦截）都在，Bug 1~4 的修复真实存在于代码中。**
缺口集中在四处：**接口面**（无列表）、**身份与归属**（谁都能推进任何订单）、**校验**（金额/参数/价格全部客户端说了算）、**未开垦域**（定价 §4.5、分拣上架 §10.5、门店单建档 §10.4、券-订单联动）。

## 三、第 1 步建议清单（按优先级）

**P0 —— 阻塞"员工端订单页 + 顾客下单页"及状态机叙事的**
1. `GET /api/orders` 列表接口（状态/门店筛选 + 分页）
2. 身份与归属校验：`next/pay/finalPay` 强制 staff 身份；顾客侧接口（下单/我的订单）强制 customer 身份且只能操作自己的；`storeId/customerId` 从 token 推导或校验
3. 状态机单测全覆盖：合法路径（门店 6 步 × 先付/洗后付、网单 7 步 × 两种）+ 非法路径（跳级/终态/未付清）+ **7 态死锁** + 并发条件更新
4. 并发保护：条件 UPDATE（`WHERE id=? AND status=?`）或 version 字段
5. 创建订单参数校验补齐（null/负数/金额）、订单号生成防撞（序号或雪花）
6. staffId 落库（从 token 取）

**P1 —— 顾客下单页的地基**
7. 分类/洗涤/定价接口 + 种子数据 + 精洗自动算价 + price=0 语义
8. 下单时单价由后端按 clothes_prices 计算（不信客户端）

**P2 —— 范围决策后再动**
9. 分拣/上架实现（或明确不做并写进文档）
10. 取送任务、券-订单联动、门店单自动建档

## 四、范围决策（2026-09-10 已定）

- **分拣/上架（§10.5）**：✅ **纳入本里程碑** —— 按设计放 Order 聚合内，逐明细实现 sorting + shelving
- **券-订单联动**：✅ **做轻量版** —— 下单时可选一张已抢的券抵扣金额，券标记已用（打通两个旗舰模块）
- **取送任务/地址簿**：⏸ **推迟** —— 网单只在订单上带地址/预约时间字段，状态 6→7 手动推进；`pickup_delivery`/`address_book` 标记"设计已定、实现推迟"
