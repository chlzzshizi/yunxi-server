# scripts/ —— 真机接口验收脚本

这些不是单元测试。单元测试跑在 Mockito 里、不碰 Spring 也不碰数据库；**这里的每个脚本都要打真机**：一个跑在 8081 上的后端 + Docker 里的 MySQL 和 Redis。它们验证的是"接起来到底对不对"——SQL 真的写进去了吗、状态真的推进了吗、越权真的被挡了吗。

## 为什么它们现在住在仓库里（而不是某个人的 `C:\tmp`）

2026-09-11 之前，这批脚本住在 `C:\tmp` 下。后果是它们**不在版本管理里**：

- 改了共享行为（比如 2026-09-10 的"后端算价"），没有任何东西提醒你这些脚本会受影响；
- `verify-race.sh` 从 `db11044` 起就是坏的，直到隔了一整轮口径修订才被发现——因为它压根没人跑。

那次踩的坑记在 `docs/bug-record.md` 的 **Bug 21 / Bug 22**。Bug 21 的教训原文就是"改了共享行为要把受影响的**全部**脚本列出来重跑"，但当时只在 5 个脚本里改了 1 个——**结论正确 + 没有执行 = 没修**，于是同一个根因换了张脸又犯一次（Bug 22：`verify-race.sh` 把"准备失败"报成"并发失灵"，把排查方向指反了）。

搬进仓库就是为了让改动能跟代码进同一次提交、能看见 diff、能被 review。

## 前置

```bash
docker compose up -d      # yunxi-mysql(3306) + yunxi-redis(6379)
# 后端已在 8081 起着
```

- **必须用 Git Bash 跑**。PowerShell 里的 `bash` 指向 WSL，而 WSL 里既没有 docker 命令也连不上宿主机的 localhost 代理（实测报 `execvpe(/bin/bash) failed`）。
- **后端必须是"已经跑过全部迁移"的那一版**。Flyway 在应用启动时才执行迁移 —— 换了迁移文件却不重启后端，DB 还停在上一个版本，症状是最难认的那种：`verify-coupons.sh` 会全军覆没在 `Unknown column 'used_time'` 上（B3/C2/F3），看起来像"抵扣逻辑写错了"，其实是后端没重启。跑之前对一眼：

  ```bash
  docker exec yunxi-mysql mysql -uroot -pqwaszx123 yunxi -N --default-character-set=utf8mb4 \
    -e "select group_concat(version order by installed_rank) from flyway_schema_history;"
  ```

  **别用 `select max(version)`**：`flyway_schema_history.version` 是 **VARCHAR**，`max` 走字符串比较，于是 `'9' > '10'` —— 库里有 V10 的时候它会告诉你最大版本是 9。2026-09-13 就是这么被它骗了一下的（当时差点把"V10 已执行"读成"后端没重启"）。要看装了哪些版本，`group_concat` 按 `installed_rank` 排出来才是真相。

  另一个更直接的判据：**新加的端点会不会回答**。`curl -s -X POST localhost:8081/api/orders/1/express -H "Authorization: Bearer x"` 回 `Token 无效或已过期`（401）说明这条路由在；回 404 说明跑的还是旧包。
- 需要 `curl`；脚本用 `docker exec yunxi-mysql mysql` 直连数据库核对"落库真相"。
- 演示账号：`manager/admin123`（店长）、`admin/admin123`（管理员）。

## 怎么跑

**从任何目录都行**，路径一律相对脚本自身：

```bash
bash scripts/verify-orders.sh
```

脚本中途产生的中间文件（替换占位符后的请求体、并发请求的响应）写到 `${TMPDIR:-/tmp}/yunxi-e2e/`，不污染仓库。

## 八个脚本分别证明什么

|---|---|---|---|
| `verify-auth.sh` | 36 | 认证域本身：员工/顾客登录的四条分支（密码错、用户名不存在、账号停用、无密码顾客）、注册口径（只要手机号+密码）、**手机号已存在且无密码时走"激活"而不是报错**、框架英文原文不外漏（Bug 23） | 会，但收尾删掉并**还原脚手架** |
| `verify-orders.sh` | 69 | 订单主链路：身份越权（A）、建单与中文编码（B/G）、参数校验 400 而非 500（C）、支付与状态机 `1→2→3→4→5→7`（D）、分页与归属（E）、跨店不隔离（F）、**顾客在线支付**（H：员工/顾客两种 token 各走各的门、付别人的单 → 403 而单子没被动过、现金 → 400、**持锁并发两个支付 → 恰好一 200 一 409 且钱只收一次**）、**快递单号**（I：仅网单 · 仅 6 态、长度 50 / 空白串 / 缺参 → 400、来源检查排在状态检查之前）、**网单门店可选**（J：不传 `storeId` → 200 且库里是 `NULL`、传个不存在的店 → 400、门店单的 `store_id` 没被这次改动带歪） | **会**：新建若干订单、一个 `mgr2` 测试店长（staff id=99） |
| `verify-pricing-authority.sh` | 24 | 后端算价与事务：请求体塞 `unitPrice:1.00` 不生效；不支持的组合/缺行 → 400 而不是 500；一次建单是一个事务（明细写不进去则订单不留）；管理员改价 403 **且价目表没被动过** | **会**：几条订单 |
| `verify-price.sh` | 26 | 定价域**读**接口：鉴权门槛、分类树、洗涤方式、价目表拼装、设计文档 §4.5 样例（衬衫 `15/35/8`、羽绒服 `0/60/0`） | 只读 |
| `verify-price-write.sh` | 29 | 定价**写**接口与精洗派生：叶子校验、`精洗=普洗+20` 自动派生、拒绝手填精洗、羽绒服逃生舱、落库真相、**结束前把数据还原** | 会，但自己还原 |
| `verify-race.sh` | 无计数 | CAS 并发保护：持锁 3 秒把时间窗拉长，两个 `next` 并发 → **恰好一个 200 + 一个 409**，且状态只推进一格（丢更新被挡住） | 会：一条订单 |
| `verify-coupons.sh` | 32 | 券-订单抵扣（§5.8）：券必须属于该单顾客（别人的券 → 400 **且券没被动过**）；网单/门店单**都能用券**，折后价落 `total_amount`；**使用记录三列**（`used=1` / `used_order_id` 指向本单 / `used_time` 由库写入 / 网单 `used_staff_id` 为 NULL、门店单 = 建单员工）；`pay` 按**折后**金额才算付清；并发用同一张券 → **恰好一个 200 + 一个 409，且库里只有 1 张单**（证 CAS 失败时订单真回滚了）；过期券 → 400；`/api/coupons/mine` 只含未使用 + `expired` 标记 + 员工 401；中文券名断言 **hex 字节** | **会**：每跑一次多发 4 张券，**且不回收**（见下） |

`verify-race.sh` 不数断言，靠最后一行 `==> [OK] / [FAIL]` 判定。

> `verify-orders.sh` 的 69 = 原有 38 + **H/I 两段 27** + **J 段 4**（2026-09-13 新增，当日已跑通）。
> `verify-pricing-authority.sh` 是 24 而不是旧表里的 22（步骤 4 加过两条）。
>
> **J 段为什么是 4 条而不是 1 条**：口径改成"网单门店可选"后，最省事的写法是只加 J1（不传门店 → 200）。但 J1 单独存在时，**把校验整个删掉**也能让它通过 —— 而"删掉校验"和"允许不选"在下一条断言上就会分家：传 `storeId=999` 也得照样 200。所以 J3（坏店 → 400）必须和 J1 成对，两条一起才能证明放开的是 `null` 这一种输入，不是"门店这件事不用管了"。反过来少了 J1，J3 的 400 也可能来自"没传门店"而不是"店是坏的"。J4 是**回归哨兵**：这次改的是 `orders.store_id` 的校验，最容易顺手带歪的就是门店单那条仍然必须落在店长自己店上的路径。

## 一个约定：验收门是"全部"，不是"挑几个"

`verify-orders.sh` 里有句注释值得抄在这里——**改了共享行为（算价、状态机、鉴权口径），下面这几个脚本全都要重跑**。2026-09-10 改后端算价时只重跑了 1 个，剩下 4 个里坏了 2 个都没人知道。

2026-09-12 又加一条：**动了 `JwtInterceptor` 的角色闸门，全都在射程内**——拦截器是所有 `/api/**` 的必经之路，它一改，每个脚本里的鉴权断言都可能翻面。

2026-09-13 再兑现一次：券-订单抵扣改的是 `OrderAppService.createOrder`，而**建单是每个造数据的脚本都要走的门**——`verify-orders` / `verify-price-write` / `verify-pricing-authority` / `verify-race` / `verify-stores` 五个脚本里所有"先建单、再断言"的段落全在射程内。新增的 `verify-coupons.sh` 是**加**了一层验证，不是**替换**那次全量重跑。

同一天晚上这条规矩又生效了一次：`/api/customers` 前缀下新增了顾客自助的 `/me`，闸门的**措辞**跟着从"管理员不参与顾客建档"改成"管理员不参与顾客相关操作"（原来那句话在 `/me` 上会变成一句错话）。只是改了一句提示文案，但 `verify-stores.sh` 的 B9 断言的就是这句话，所以它必须跟着改——**闸门的台词也是被测的**。

### 第三个坑：`db()` 的字集（2026-09-12）

**七个脚本里每一个**访问数据库的助手（`db()` / `dbFile()` / 内联的 `docker exec`）现在都带 `--default-character-set=utf8mb4`，**别把这个参数删了**。删掉之后 mysql 命令行会按客户端默认的 latin1 收发，中文两个方向都坏：

- 写 → UTF-8 字节被当 latin1 解读再转存 = 双重编码（实测存进去是 `C3A4C2BAE28098…`）
- 读 → 真 UTF-8 的中文转不成 latin1，整串变成 `?????`

**最阴的是双重编码在「读」的时候会抵消回去**：存的是乱的，`SELECT` 出来却是好的。于是"列表里不含这个店名"这类断言**无条件通过**——库里那个名字本来就写不出正确的那六个字，怎么断言都找不到它。`verify-stores.sh` 的 A3 当时就是这么假绿的。

所以造完中文数据要**断言库里的字节**（`verify-stores.sh` 的准备守卫 + A3c 就是干这个的），不能只看"读出来是对的"。

> 完整的两类编码坑（还有一类是 MSYS2 把非 ASCII 命令行参数转成 GBK，影响 `curl -d`）写在 `verify-stores.sh` 的文件头，要改脚本先读那段。

### 表格里的断言数是快照

上面那张表的数字是**最后一次全量跑的结果**，不是自动维护的。改了脚本就得回来手工更新——这不是理想状态，但它至少是一个能被 review 的 diff；不写反而没人知道哪个脚本变过。跑一遍对不上就顺手改了。

## 写脚本时的两条硬要求

1. **准备阶段失败要立刻喊停，不能让它继续跑成断言失败。** 拿不到订单 id、状态没到预期、登录没拿到 token —— 直接打印原始响应并 `exit 1`。否则报出来的错会指向完全无关的地方（Bug 22 就是这么把两个 404 读成"CAS 失灵"的）。
2. **中间的 `404 资源不存在` 出现在"资源一定存在"的用例里，本身就是强信号。** 别把它当成"断言没通过"轻轻放过。

## 已知的脏数据

脚本直连数据库，跑完会在库里留下痕迹：`orders` 表的新订单（含中文备注的样例单）、若干注册的顾客。演示前若要干净数据，`down -v` 重建卷再跑一遍迁移即可。

三处**故意保留**的脚手架（脚本每次运行都会把它们自愈成正确状态，删了下次跑会自动重建）：`stores` id=2「二号门店」与 `staff` id=99 的 `mgr2`（verify-orders 的 F 段用）、`stores` id=99「云洗停业测试店」（verify-stores 的 A3 用）。

`verify-coupons.sh` 的脚手架是**累积型**，和前三个不一样：它每跑一次就新发 4 张券（**不改 id、不复用**），跑 N 次库里就有 4N 张叫做 `CPN-E2E-*` / 「开业五折券」的券，顾客A 名下一堆已用掉的抢券记录。之所以不复用固定 id：券的可用性绑定在"这个批次还能不能抢"上，复用就得每次重置 Redis 的库存键和已抢集合，那等于把"准备阶段"变成一段容易写错的 SQL；而每轮新发一张的代价只是几张废券。**要干净数据只有 `down -v`**。
